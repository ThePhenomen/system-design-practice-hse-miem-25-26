## Этап 1

Для эффективного отслеживания состояния наших веб-серверов на текущем этапе достаточно собирать базовые метрики: общее количество запросов в системе и HTTP-статусы всех запросов. Анализ Error Rate позволяет быстро выявлять проблемы, даже если их процентное соотношение незначительно.
Однако для комплексного мониторинга базы данных и работы имеющихся серверов с ней рекомендуется расширить набор метрик следующими показателями:
* Общее количество ошибок при работе с БД - отображает текущего состояния базы данных, позволяет оперативно реагировать на возникающие проблемы
* Количество медленных запросов - позволяет своевременно выявить необходимость оптимизации работы с базой данных через добавление индексов, рефакторинг запросов или настройку кэширования
* Статистика подключений к БД - включает в себя:
    * Общее количество подключений (open)
    * Количество занятых подключений (in_user)
    * Количество простаивающих подключений (idle)
    
* Количество запросов, ожидающих подключения к БД - позволяет совместо со статистикой подключений к БД  оптимально настроить параметр max_connections.
Эти метрики в совокупности позволяют более точно диагностировать потенциальные проблемы в работе веб-серверов и базы данных.

## Этап 2

Кастомный скрипт для нагрузочного тестирования (находится по пути `/demo-app-1/k6/scripts/custom-load-script.js`)

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export let options = {
  scenarios: {
    storm: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '10s', target: 1000 },
        { duration: '10s', target: 1000 },
        { duration: '10s', target: 0 },
      ],
    },
    wave: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '2m', target: 500 },
        { duration: '30s', target: 500 },
        { duration: '30s', target: 0 },
      ],
    },
    mixed: {
      executor: 'constant-vus',
      vus: 50,
      duration: '2m',
    },
  },
};

function randomInt(min, max) {
  return Math.floor(Math.random() * (max - min + 1)) + min;
}

export default function() {
  if (Math.random() < 0.8) {
    const payload = JSON.stringify({
      user_id: randomInt(1, 2),
      amount: Math.random() * 100,
      description: 'k6 test'
    });

    const res = http.post('http://localhost:8081/api/orders', payload, {
      headers: { 'Content-Type': 'application/json' }
    });

    check(res, {
      'order created': (r) => r.status === 200 || r.status === 201
    });
  } else {
    const res = http.get('http://localhost:8081/api/orders');
    check(res, {
      'list ok': (r) => r.status === 200
    });
  }

  sleep(0.05);
}
```

В данном скрипте, помимо нагрузки вида "Шторм" и "Волна", промоделирована реалистичная нагрузка, при которой n пользователей (в данном случае 50), непрерывно находятся на сайте и делают запросы, что позволяет узнать, как ведет себя система при штатных условиях.

## Этап 3

После прогона нагрузочного тестирования выявились следующие проблемы:
* Буквально в самом начале тестирования начинает возникать проблема, связанная со значением параметра max_connections у БД - если количество соединений начинает превышать указанное значение (200 в случае имеющейся БД), то прочие запросы начинают отваливаться с ошибкой "pq: sorry, too many clients already". Количество подобных ошибок отображается в метрике `db_errors_total`.
* Через некоторое время начинает возникать следующая ошибка "connect: cannot assign requested address" - системная ошибк, связанная с нехваткой ресурсов для создания сетевого соединения. Вероятно, это может быть связано с параметром ядра net.core.somaxconn и может быть устранено за счет "тюнинга" параметров Docker и ядра
* После окончания тестирования в метрике `db_errors_total` имеются ошибки, возникшие при выполнении запроса list_orders (GET запрос на эндпоинт /api/orders).

## Этап 4

Возможные улучшения имеющейся системы:
* Добавить репликацию master-slave БД для обеспечения отказоустойчивости, а также для распределения запросов на чтение и на запись - данное решение может помочь устранить 3 проблему из предыдущего этапа
* Добавить комплексное логирование веб-серверов и централизованный сбор логов с использованием Elasticsearch/Opensearch - данное решение позволит быстрее определять проблемные места в работе backend-сервисов
* Более тонко настроить параметры базы данных - изменить параметр max_connections (и настроить ограничение данного параметра на самих веб-сервисах) и другие параметры, которые позволят избежать проблемы "pq: sorry, too many clients already" и ей подобных
* Обеспечить отказоустойчивость балансировщиков - в текущей архитектуре единственный экземпляр является "узким горлышком", и его выход из строя повлечет полную недоступность системы
